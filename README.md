# SentinelOps Backend — Production Setup

## Render environment variables

Set these in Render (do not commit real values):

- DATABASE_URL — Supabase PostgreSQL connection string
- JWT_SECRET — long random secret used to sign login tokens
- NODE_ENV=production
- FRONTEND_URLS — deployed frontend origin(s), comma-separated
- ADMIN1_NAME / ADMIN1_EMAIL / ADMIN1_PASSWORD — first administrator bootstrap
- ADMIN2_NAME / ADMIN2_EMAIL / ADMIN2_PASSWORD — second administrator bootstrap

For initial testing, FRONTEND_URLS can be empty; CORS will allow requests.
Before production launch, set it to your real frontend origin.

## What this version fixes

- Persistent PostgreSQL-backed users
- Registration
- bcrypt password hashing
- Real password verification during login
- JWT authentication
- `/auth/me`
- Admin user listing
- Admin account approval
- Database schema initialization
- `/health` checks the database
- `/` route
- Production PostgreSQL SSL

## Important

The existing Supabase `users` table is empty, so no existing production users need to be migrated.

After deploying this backend, register a test account through:

POST /auth/register

with JSON:

{"email":"test@example.com","password":"at-least-8-chars"}

The account will be created with `approved=false`. An admin account must exist before the approval endpoint can be used.

## Creating the first admin

For safety, this package does not automatically promote an arbitrary first user to admin.

Use Supabase SQL Editor to create/convert a controlled administrator account only after deciding the admin email and password. The password_hash must be a bcrypt hash generated by the application (not plaintext).

A convenient approach is to temporarily run the bcrypt hash command locally, then insert the hash with SQL.

Do not put plaintext passwords into the database.

## Frontend API contract

Register:
POST /auth/register
{ "email": "...", "password": "..." }

Login:
POST /auth/login
{ "email": "...", "password": "..." }

Authenticated requests:
Authorization: Bearer <token>

Current user:
GET /auth/me

Admin list:
GET /admin/users

Approve:
PATCH /admin/users/:id/approve

Health:
GET /health


## Two administrator accounts

Set the six ADMIN1/ADMIN2 variables in Render. On startup, the backend creates or updates those two accounts as:

- role = admin
- approved = true

Passwords are bcrypt-hashed before being stored. Do not put these credentials in GitHub or `.env` committed to the repository.

The bootstrap runs on every startup and intentionally keeps those two configured accounts approved/admin. If you later change an admin password, update the corresponding Render environment variable and redeploy.
