# SentinelOps Backend — Production Setup

## Render environment variables

Set these in Render (do not commit real values):

- DATABASE_URL — Supabase PostgreSQL connection string
- JWT_SECRET — long random secret used to sign login tokens
- NODE_ENV=production
- FRONTEND_URLS — deployed frontend origin(s), comma-separated
- ADMIN1_NAME / ADMIN1_EMAIL / ADMIN1_PASSWORD — first administrator bootstrap
- ADMIN2_NAME / ADMIN2_EMAIL / ADMIN2_PASSWORD — second administrator bootstrap

For initial testing, FRONTEND_URLS can be empty; CORS will allow requests.
Before production launch, set it to your real frontend origin.

## Demo data safety

The demo seed is disabled unless `ALLOW_DEMO_SEED=true` and must only be run against an isolated PostgreSQL database. It requires `DEMO_SEED_PASSWORD` from the environment, creates deterministic marked records for Tushar, Deepanshu, Suraj, Aditya and Vansh, and refuses to touch non-demo records.

Run it only in an isolated environment:

```text
ALLOW_DEMO_SEED=true DEMO_SEED_PASSWORD='local-only-password' npm run seed:demo
```

The script is idempotent. It does not run during application startup.

## Registration

Register a test account through:

POST /auth/register

with JSON:

{"email":"test@example.com","password":"at-least-8-chars"}

The account will be created with `approved=false`. An admin account must exist before the approval endpoint can be used.

## Creating the first admin

For safety, this package does not automatically promote an arbitrary first user to admin.

Use Supabase SQL Editor to create/convert a controlled administrator account only after deciding the admin email and password. The password_hash must be a bcrypt hash generated by the application (not plaintext).

A convenient approach is to temporarily run the bcrypt hash command locally, then insert the hash with SQL.

Do not put plaintext passwords into the database.

## Windows network sensor

The cloud website cannot inspect a laptop's Wi-Fi adapter or local LAN. Run the documented PowerShell sensor from `sensor/README.md` on the authorized Windows laptop.

The flow is:

1. An administrator obtains a normal SentinelOps access token and runs `POST /sensors/enroll` from PowerShell with `X-SentinelOps-Enrollment: powershell`. The response contains the sensor secret once.
2. The operator stores the secret in the DPAPI-protected `ProgramData\SentinelOps\sensor.json` file using the commands in `sensor/README.md`.
3. The sensor sends HTTPS `POST /sensor/v1/heartbeat` and `POST /sensor/v1/snapshots` using `X-Sensor-ID` and `X-Sensor-Secret` headers. The browser never receives those credentials.
4. Authenticated website users can read `GET /sensors`, `GET /network/overview`, `GET /network/snapshots`, `GET /network/interfaces`, `GET /network/devices`, and the existing `GET /assets` endpoint. Sensor-derived assets have `source: "sensor"` and `isDemo: false`.

The default sensor mode reads Windows' local neighbour table. Explicit subnet discovery (`-DiscoveryMode subnet -SubnetCidr ...`) and TCP availability checks (`-ServicePorts ...`) are opt-in, bounded, low-rate, and read-only. Values include timestamps and collection methods; unavailable values remain unavailable. A sensor is `active` only after a recent heartbeat and becomes `stale` after three heartbeat intervals. A changed SSID/BSSID/local address/subnet/gateway is stored as an informational observed-fact alert, not as a claim of malicious activity.

Telemetry ingestion requires HTTPS, validates bounded payloads and IP/MAC fields, rate-limits each sensor/IP, hashes credentials with bcrypt, scopes reads to the owning user (or an administrator), and rejects duplicate `(sensor, client_observation_id)` snapshots. Revoke a sensor with `POST /sensors/:id/revoke`.


## SMTP password reset configuration

Production password-reset delivery remains disabled until the following Render environment variables are configured:

- `SMTP_HOST`
- `SMTP_PORT`
- `SMTP_SECURE`
- `SMTP_USER`
- `SMTP_PASSWORD`
- `MAIL_FROM`
- `PASSWORD_RESET_ORIGIN`

`GET /health/email` reports only whether the required SMTP values are present; it never returns their values.

## Two administrator accounts

Set the six ADMIN1/ADMIN2 variables in Render. On startup, the backend creates a missing configured account as:

- role = admin
- approved = true

Passwords are bcrypt-hashed before being stored. Do not put these credentials in GitHub or `.env` committed to the repository.

Existing accounts are not overwritten by startup bootstrap. Password changes must use the authenticated password-change flow or an explicitly approved administrative procedure.
